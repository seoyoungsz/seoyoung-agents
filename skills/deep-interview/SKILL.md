# Deep Interview

요구사항을 명확히 하고(Phase 1), 기획서에 없는 구현 레벨 결정을 점검한 후(Phase 2) planner에게 넘긴다.

원칙: 질문을 한꺼번에 쏟아내지 않는다. 가장 큰 불확실성을 하나씩 해소한다.

## 입력 컨텍스트

호출자(`/task`, `/plan`)가 이미 확보한 데이터가 있으면 인터뷰 시작 전에 전달받는다:

- **Linear 이슈 메타데이터** — 제목, 설명, 상태 등
- **Notion extracted 데이터** — 기획 문서에서 추출한 요구사항

이미 명확한 축은 질문하지 않는다. 예: Linear 이슈에 목표가 명시되어 있으면 Goal 질문을 건너뛴다. Notion extracted가 4축(goal, scope, constraints, completion criteria)을 모두 충족하면 Phase 1을 건너뛰고 Phase 2(개발자 체크리스트)부터 시작한다. Phase 2는 항상 실행된다.

단독 호출(`/deep-interview`) 시에는 입력 컨텍스트 없이 시작한다.

## 질문 축

아래 순서대로 가장 불명확한 축을 선택한다:

1. **목표 (Goal)** — 무엇을 달성하려는가
2. **범위 (Scope)** — 포함/제외 범위
3. **제약 (Constraints)** — 기술적, 시간적, 자원 제약
4. **완료 기준 (Completion criteria)** — 어떻게 되면 끝인가

기존 맥락과 영향 범위(어떤 패키지/파일이 영향받는가)는 사용자에게 묻지 않는다. 오케스트레이터가 코드베이스를 직접 확인하여 bootstrap context에 추가한다.

코드베이스를 보면 답할 수 있는 질문은 사용자에게 묻지 않고 직접 확인한다.

## 진행 방식

한 번에 하나의 질문만 한다. 각 질문은 아래 구조를 따른다:

```
현재 이해: {요청에 대한 한 문장 요약}
막힌 결정: {가장 중요한 불확실성}
추천 답안: {추천하는 답, 있는 경우}
질문: {하나의 질문}
```

각 답변 후 결정된 사항을 간략히 업데이트한다. 의미 있는 불확실성이 남아 있을 때만 다음 질문을 한다. 도움이 될 때 2~3개 선택지를 제시하되, 자유 입력을 항상 허용한다.

## Phase 1 종료 기준

아래가 모두 명확해지면 Phase 1(요구사항 인터뷰)을 종료한다:

- 달성할 목표
- 포함/제외 범위
- 지켜야 할 제약
- 완료 기준

인터뷰 중 해결할 수 없는 질문이 남으면 인터뷰를 종료하지 않고 사용자에게 답을 구한다. 모든 축이 명확해야 Phase 2로 진행할 수 있다.

## Phase 2: 개발자 체크리스트

Phase 1에서 요구사항이 확정되면, 기획서에 명시되지 않지만 구현 시 결정이 필요한 항목을 점검한다.

### scope 결정

scope option으로 질문 우선순위를 조절한다. option은 **배제 필터가 아니라 우선순위 필터**다 — `scope: frontend`여도 공통 항목(보안, 테스트)은 생략하지 않는다.

| option | 동작 |
|--------|------|
| `auto` (기본값) | Phase 1 결과에서 도메인을 추론. 불확실하면 사용자에게 질문 |
| `frontend` | 프론트 항목 우선, 백엔드/인프라는 최소 확인만 |
| `backend` | 백엔드 항목 우선, 프론트/인프라는 최소 확인만 |
| `infra` | 인프라 항목 우선, 프론트/백엔드는 최소 확인만 |
| `fullstack` | 전체 항목 |

단독 호출 시 첫 번째 인자로 scope를 지정할 수 있다: `/deep-interview frontend`. 예약어(`frontend`, `backend`, `infra`, `fullstack`)가 오면 scope로 인식하고, 그 외 텍스트는 요청 맥락으로 처리한다. 생략하면 `auto`.

### 체크리스트 항목

#### 티어 1 — 핵심 (항상 확인)

| # | 항목 | 축 | 질문 예시 |
|---|------|----|----------|
| 1 | 데이터 방식 | 공통 | Mock으로 시작할지, 실제 API를 바로 연결할지 |
| 2 | 에러 상태 | 공통 | API 실패, 빈 목록, 타임아웃 시 어떻게 보여줄지 |
| 3 | 성공 기준 | 공통 | Phase 1의 완료 기준과 별개로 기술적 수용 기준이 있는지 |
| 4 | 테스트 전략 | 공통 | 단위/통합/E2E 중 어디까지 커버할지 |
| 5 | 보안 | 공통 | API 키/토큰 관리 방식, 인증/인가 요구사항 |

#### 티어 2 — 조건부 (scope와 위험도에 따라)

| # | 항목 | 축 | 조건 |
|---|------|----|------|
| 6 | 로딩 상태 | 프론트 | scope가 frontend/fullstack/auto(프론트 포함) |
| 7 | 접근성 (a11y) | 프론트 | scope가 frontend/fullstack/auto(프론트 포함) |
| 8 | 반응형 | 프론트 | scope가 frontend/fullstack/auto(프론트 포함) |
| 9 | 사용자 역할/권한 | 백엔드 | 다중 사용자 또는 관리자 기능이 있는 경우 |
| 10 | 저장/동기화 정책 | 백엔드 | 폼, 편집기 등 사용자 입력이 있는 경우 |
| 11 | 국제화 (i18n) | 프론트 | 다국어 지원이 필요하거나 날짜/통화 형식이 관련된 경우 |
| 12 | 성능 기준 | 인프라 | 대량 데이터, 동시접속, 가상화가 필요할 수 있는 경우 |
| 13 | 모니터링 | 인프라 | 프로덕션 배포가 예정된 경우 |
| 14 | CI/CD | 인프라 | 새 서비스 추가 또는 배포 파이프라인 변경이 필요한 경우 |

### 분기 로직

앞 질문의 답이 뒤 질문의 깊이를 조절한다:

| 선행 답변 | 영향 |
|----------|------|
| 데이터 방식 = Mock | 에러 상태 → "Mock 단계에서는 기본 에러 UI만" 기본값 제안, 성능 기준 스킵 |
| 데이터 방식 = 실제 API | 에러 상태 → 구체적 시나리오별 질문 (실패/빈 목록/타임아웃) |
| 보안 = 인증 없음 | 사용자 역할/권한 스킵 |
| scope = 프론트 only | 저장/동기화 → 클라이언트 측 임시저장만 질문 |

### 진행 방식

Phase 1과 같은 원칙을 따른다:

- Phase 1에서 이미 답이 나온 항목은 다시 묻지 않는다
- 한 번에 전체를 묻지 않는다. **누락된 고위험 항목만 묶어서 2~3개씩 질문**한다
- 각 질문에 합리적인 기본값을 제안한다. 사용자가 "기본값으로" 또는 "알아서"라고 하면 기본값을 채택하되 **가정**으로 표시한다
- 체크리스트 결과가 Phase 1의 scope를 넘어서는 경우(예: i18n 추가 → 새 의존성 필요), 반드시 사용자에게 범위 확장 확인을 받는다

### Phase 2 종료 기준

티어 1 항목이 모두 결정(confirmed 또는 assumptions)되고, 해당하는 티어 2 항목도 결정되면 종료한다. 모든 항목에 답이 필요한 것은 아니다 — 해당하지 않는 조건의 티어 2 항목은 스킵한다.

단, 사용자가 "지금 결정할 수 없다"고 명시적으로 보류한 항목은 unresolved로 기록하고 종료를 차단하지 않는다. unresolved는 사용자의 명시적 보류 의사가 있을 때만 허용된다 — 에이전트가 자의적으로 unresolved로 분류하지 않는다.

## 출력 계약

종료 시 전체 대화록이 아니라 결정사항만 요약한다. 아래 top-level YAML 형태를 그대로 출력한다. 래퍼(`skill_result` 등)로 감싸지 않는다.

```yaml
interview_result:
  goal: "..."
  scope_in: [...]
  scope_out: [...]
  constraints: [...]
  completion_criteria: [...]
  preflight:
    scope: auto | frontend | backend | infra | fullstack
    confirmed:
      - { item: "데이터 방식", decision: "실제 API 연결", axis: "공통" }
      - { item: "에러 상태", decision: "toast + retry 버튼", axis: "공통" }
    assumptions:
      - { item: "로딩 상태", decision: "스켈레톤 UI (기본값 채택)", axis: "프론트" }
    unresolved:
      - { item: "모니터링", reason: "인프라팀 확인 필요", axis: "인프라" }
```

`preflight` 섹션의 각 항목은 아래 분류 중 하나에 속한다:
- **confirmed** — 사용자가 명시적으로 결정한 항목
- **assumptions** — 기본값을 채택한 항목. 구현 중 재확인이 필요할 수 있음
- **unresolved** — 결정하지 못한 항목. reason 필드에 왜 미결인지 기록

## 역할 경계

이 skill은 **요구사항 명확화 전용**이다. bootstrap context 완성(영향받는 패키지/디렉토리 목록, sensor-binding 결과 추가)은 호출자(`/task`, `/plan`)의 책임이다.

단독 호출 시(`/deep-interview`) `interview_result`만 출력하고 종료한다. planner spawn이나 구현은 하지 않는다.

## 유사 도구와의 구분

- `clarify:vague` — 범용 요구사항 명확화. deep-interview는 이 프로젝트의 planner bootstrap에 특화된 4축 구조와 `interview_result` YAML 출력을 제공한다.
- `ce-brainstorm` — 탐색적 아이디어 발산. deep-interview는 이미 방향이 정해진 요청의 불확실성을 해소한다.
